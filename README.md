# WasteSort – Thesis Prototype

Android prototype (Kotlin / Jetpack Compose) for the Bachelor thesis *"Bachelor thesis in AI, Sustainability and Applied Technology"* at Tomorrow University of Applied Sciences. The app is the experimental instrument of the study: it investigates whether a **child-friendly AI user interface** helps families sort waste more correctly, compared to a conventional, text-based interface — based on the official waste-sorting rules of the city of Bergisch Gladbach.

Package: `de.tou.wastesort` · minSdk 26 · targetSdk/compileSdk 35 · Kotlin 2.0.21 · AGP 8.5.2

## What it does

Participants scan 20 physical stimulus cards (each with a photo of the waste item + a QR code) one after another with the app. For each card, the app shows an AI estimate of the correct waste bin along with a confidence score, after which the participant chooses a bin themselves. Every decision is logged locally (time, response, ground truth, AI suggestion, confidence) and can be exported as a CSV file at the end.

The app comes in two interface variants that render **the same underlying response data** differently:

- **Version A – Text**: conventional, adult-oriented presentation (category text, percentage confidence as a progress bar, warning notice for low confidence). Fully in German (the study's target language).
- **Version B – Child-friendly**: large colored bin icons, short child-friendly wording, redundant cues (color **and** icon **and** text, never color alone), a 5-star confidence display instead of a raw percentage, and an explicit uncertainty state ("🤔 I'm not sure — ask a grown-up").

The variant can be switched at any time via a toggle in the app (for counterbalanced sessions this is controlled manually by the facilitator, see [Known Limitations](#known-limitations)).

## QR-Code Stimulus Workflow

Important for the study design: **the QR code on each card does not classify anything.** It is purely a stable identifier (`BG-WASTE-01` … `BG-WASTE-20`) that maps to a fixed dataset in `StimulusRepository.kt`. This ensures that *every* participant sees the exact same AI response for a given item — independent of lighting, camera angle, or actual image-recognition accuracy.

```
StudyConfig.STUDY_MODE = "qr_predefined"
```

App flow: **Scan** → camera opens → QR code detected → item loaded → **recommendation screen** (Version A or B) → participant selects a bin → **next item**. Unknown/invalid QR codes are handled cleanly without crashing ("This card is not part of the study set" / child-friendly: "Oops! I don't know this card") — there is **no** fallback to a random recommendation.

### Why TrashAI doesn't run live

The prototype originally used live classification via the Roboflow/TrashAI API (`classifier/RoboflowTrashAiClient.kt`, model `trash-ai/4`). Live recognition turned out to be too inaccurate for reliable study results, so the actual data collection switched to the QR-based, fixed dataset instead. The TrashAI client code remains in the project (for development/documentation purposes) but is **not** called by the active study workflow.

### Legacy QR format of the already-printed setcards

The physical setcards (`Setcard_01_...png` … `Setcard_20_...png`) were generated by an earlier script and encode metadata rather than the short `stimulusId` (format `"Nr: 9; Set: 1; Gegenstand: Apfelrest"` instead of `"BG-WASTE-09"`). So these cards don't need to be reprinted, `StimulusRepository.resolveFromQrPayload()` resolves both formats: it first tries the exact `stimulusId`, and falls back to parsing the number after `"Nr: "` and resolving it via `itemNumber`.

## Build & Run

1. Open in Android Studio (Gradle sync runs automatically via the Gradle wrapper, AGP 8.5.2 / Kotlin 2.0.21).
2. Select a run configuration of type **Android App** (not `connectedDebugAndroidTest`) and launch it on a device/emulator with API 26+.
3. Required permission: camera (for QR scanning); no internet access is needed in study mode.
4. Unit tests (JVM, no device needed):
   ```
   ./gradlew test
   ```

### Facilitator debug view

Long-pressing the app title on the start screen opens a debug view listing all 20 mappings (ground truth, prototype response, confidence, unclear flag) without scanning any card — useful to verify the dataset before a data-collection session.

### Regenerating QR codes

```
pip install qrcode[pil]
python tools/generate_qr_codes.py
```
Deterministically generates `BG-WASTE-01.png` … `BG-WASTE-20.png` plus a printable overview sheet. Already-printed setcards using the legacy format remain fully functional (see above).

## Data Collection & Export

Every decision is logged as a CSV row stored locally on the device (no cloud, no network access), with at least: `participant_id, session_id, trial_id, timestamp, ui_variant, stimulus_id, item_number, item_name_de, ground_truth_category, prototype_response, confidence, unclear_flag, participant_response, is_correct, response_time`. Exporting/sharing the CSV file happens via the `ExportScreen` (Android share intent via `FileProvider`).

## Known Limitations

- The A/B variant is switched manually within the app; automatic AB/BA counterbalancing per participant is not hard-enforced in the app and must be managed by the facilitator.
- For items 2 (adhesive tape), 3 (diaper), and 4 (CD/DVD), there is no verbatim match in the official sorting guide; the assignment follows established disposal convention (see code comment in `StimulusRepository.kt`).
- The legacy QR codes on the already-printed setcards contain a cosmetic umlaut-encoding bug in the free text; this does not affect functionality, since only the numeric prefix (`Nr: <n>`) is parsed.
- The live TrashAI integration (`classifier/`, `mapping/`) is functionally present but not part of the active study path and was not optimized for production-level accuracy.
